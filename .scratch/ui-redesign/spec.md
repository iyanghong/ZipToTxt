# 桌面界面外观与操作流程优化

Status: ready-for-human

讨论日期：2026-10-08。用户提出“优化 UI 界面，使得更美观、更便捷”，已选择 B 侧栏工作区，并要求调整方案后再实施。

## 改造前的现状

桌面界面使用 Tkinter 与 ttk，CLI 和归档处理逻辑独立。主窗口以纵向表单展示操作、源路径、Git 选择、输出目录、分片大小、密码、处理状态和结果路径。压缩与还原通过单选项切换。

Git 提交选择和打包文件清单使用独立模态窗口。当前确认提交后先预览清单，回到主窗口填写密码；开始压缩时再次核对并确认清单。提交窗口已经具备分支关键字、日期快捷项与日历、作者筛选、逐行勾选、批量选择和加载更多。文件清单展示可打包数量、未压缩总大小和缺失文件。

当前任务通过后台线程执行，主窗口提供阶段文字与忙碌状态。完成或失败会弹窗，成功后可以打开输出目录。没有密码显示开关、复制结果路径按钮或跨次启动的界面偏好保存。

## 沿用的产品规则

- 压缩和还原均允许指定输出目录，在其下创建新目录，不覆盖已有结果。
- 文本分片大小默认 50 MB，可配置；密码加密及跨平台归档格式保持既有约定。
- 提交变更文件包只包含所选目录及其子目录内的去重路径，实际读取当前磁盘内容；缺失文件列明并跳过，全部缺失时不能生成空包。
- 系统缺少 Git 时禁用提交选择，普通压缩和还原仍可使用。
- 一次处理一个文件或目录；处理中保持界面响应，完成后可继续使用。

## 已确认的设计方向

1. 清爽浅色、蓝色主按钮、统一留白与字体层级，继续使用桌面控件。
2. Git 提交选择和打包文件清单合并到同一窗口，左侧筛选并勾选提交，右侧查看文件清单和数量。
3. 加入密码显示／隐藏、复制输出路径、记住上次目录和分片大小，不保存密码；完成结果直接显示在窗口内。
4. 主要场景为普通压缩与还原，以此决定主界面的默认入口和信息布局。

## 已确认的流程细节

勾选提交后自动在后台更新打包文件清单、可打包数量、未压缩总大小和缺失项，更新期间保持界面响应。连续改变勾选时，以最新选择对应的清单为准，旧任务结果不能覆盖新清单；清单未就绪或没有可打包文件时不能确认。

开始打包时重新检查文件清单。文件范围和缺失状态未变化就直接开始，有变化则重新展示并确认。文件内容继续取当前磁盘版本，不能把此前预览的内容视作固定版本。

## 布局预览与最终确认

预览为 `ui.prototype.html`，使用示例数据，无真实归档操作。URL 参数 `variant=A/B/C` 与底部箭头切换主窗口结构：

- A：标签页表单，路径与输出、分片与密码分组。
- B：侧栏工作区，路径与参数左右分栏。
- C：分步向导，逐步选择路径、设置参数、确认开始。

用户选择 B，并在完整范围确认项中选择“先调整方案”。三种结构都附带提交选择与文件清单的合并窗口示意。预览代表布局、颜色和信息层级，具体桌面控件的外观与尺寸按平台适配。

## 新增要求

1. 压缩和解压显示真实进度条。用户确认采用各阶段准确百分比，并显示已处理／总大小：压缩文件、加密生成 TXT、校验解密 TXT、解压文件各阶段独立计算，不增加综合百分比。现有核心只回传阶段文字，ZIP 写入与解压使用整文件接口，需要按实际处理的字节统计并回传进度；不可仅按时间推进。扫描和获取总量时没有可用分母，显示正在扫描／准备；大文件采用分块处理，界面持续接收进度。空文件／空目录能够正常完成，错误不得显示为处理成功。
2. Git 提交列表增加独立“用户”列，展示提交作者姓名及邮箱，与按作者筛选的语义一致。现有数据已经包含这两项，界面单独展示，不在时间单元格中合并用户。

进度显示方式和用户列要求已确认，B 预览已更新。预览中的进度仅为演示；真实程序使用实际字节计数。用户于 2026-10-08 确认：“确认，请开始实现，最后打包出3个平台的发布包。”完整范围已确认，开始实施。

## 后续确认

采用现有 Tkinter／ttk 和系统文件选择对话框；主窗口明确区分压缩与还原，输出位置给出目录名称提示，阶段状态与完成结果具有固定显示区域。窗口缩放和控件尺寸需要兼顾三个平台，较小可用区域不能使关键操作无法访问。

非密码偏好保存在当前用户的本机配置目录；密码和确认密码不写入配置，任务结束后清空。配置缺失或损坏不影响启动，过期目录允许重新选择。保留现有清理、不覆盖和归档格式约定。

方案确认后更新状态并实施，覆盖真实控件交互、设置记忆、合并窗口的异步预览和文件状态变化、加密还原回归；按既有流程重新构建 macOS arm64、Windows x86_64、Linux x86_64 的本地绿色产物。各平台实测环境及局限分别记录，发布到 GitHub 不属于本次默认范围。
