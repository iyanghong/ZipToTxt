# 2026-09-29 末尾空字节兼容修复实测

## 现场文件

报告中的 `ls` 目录共有 4 个文本分片。前 3 个文件实际各为 50,000,001 字节，第 4 个为 30,988,913 字节；每个文件末尾都多了一个 `0x00`（NUL）。去掉这个字节后，Base64 内容分别为 50,000,000、50,000,000、50,000,000 和 30,988,912 字节。旧版按文件总大小拒绝第一片，与截图中的报错一致。尚未确定空字节是在生成、保存还是传输时加入的。

初次检查还发现一个独立的数据问题：`part-000003.txt` 与 `part-000002.txt` 完全相同，内部序号均为 2，真正的第 3 片缺失。用户随后重新复制了第 3 片；复查确认四片序号依次为 1、2、3、4，总片数均为 4，盐和归档标识一致，内容各不相同，Base64 与兼容后的大小检查全部通过。检查期间未修改原始文件，也未取得用户的密码，因此未完成这套实际归档的密码认证和最终还原。

## 修复范围

共享的 `decrypt_path` 只兼容单个末尾 NUL，再检查 Base64 内容大小。新生成的 TXT 仍不超过 50,000,000 字节。内部 NUL、多个末尾 NUL、其他非法 Base64、错误密码、分片序号错误及混合归档继续报错；AES-GCM 认证保持有效。
